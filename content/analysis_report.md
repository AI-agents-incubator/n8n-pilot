# Анализ спецификации n8n Pilot (v3.0)

Внимательно изучил новую версию технического задания `SPEC.md`. Архитектура (PIVOT v2.0) с Injected Side Panel, Shadow DOM и локальным роутингом выглядит прочной и устраняет главные недостатки прошлых решений. 

Однако я обнаружил несколько логических «дыр», потенциальных проблем архитектуры Manifest V3 и недостающих требований, которые стоит проработать.

## 1. Проблемы безопасности и хранения (Crypto)
**Отмечено в спецификации:** Пароли и API-ключи шифруются AES-256-GCM, ключ хранится в `chrome.storage.local`.
**Где дыра:** Хранение ключа шифрования в том же самом хранилище, что и зашифрованные данные, защищает только от базовых XSS, но бессильно против кражи профиля Chrome (malware) или доступа к файловой системе. 
**Предложение:** 
- Добавить опциональный **Master Password** (вводится при старте сессии, хранится только in-memory браузера). Ключ шифрования выводится через PBKDF2. Если пароль не задан, использовать текущий fallback (предупредив пользователя о рисках).

## 2. Жизненный цикл Background Service Worker (MV3)
**Отмечено в спецификации:** Background service worker поддерживает стриминг токенов от Claude API и пересылает их в content script (Section 17.3). 
**Где дыра:** В Manifest V3 service workers агрессивно усыпляются браузером при неактивности или по истечении времени (обычно 5 минут максимум). Длинный стриминг вывода (или долгое ожидание ответа от LLM) может привести к тому, что воркер "умрет", разорвав SSE-соединение и сломав UI.
**Предложение:** 
- Внедрить механизм **Keep-Alive** связи (периодический ping из content.js в background.js) во время активной генерации, чтобы предотвратить suspend воркера браузером.

## 3. Ограничения n8n API и Payload Size
**Отмечено в спецификации:** Content script запрашивает `/api/v1/executions` для показа логов.
**Где дыра:** Executions в n8n могут содержать огромные объемы бинарных данных или многомегабайтные JSON (сотни элементов). Попытка загрузить и отрендерить их в UI расширения без лимитов приведет к утечкам памяти (OOM) и падению вкладки браузера.
**Предложение:** 
- В `N8nClient` при запросе executions необходимо явно использовать query-параметр `includeData=false` (если поддерживается API n8n) для таблиц списков или обрезать данные до определенного размера.

## 4. Множественные окружения (Environments)
**Отмечено в спецификации:** Settings содержат один `n8nBaseUrl`. Content script инжектится только на URL, совпадающий с ним.
**Где дыра:** Продвинутые пользователи (текущая ЦА) часто используют несколько инстансов n8n (Local/Dev, Staging, Prod). Привязка к одному URL ограничит полезность. Изменение URL в настройках каждый раз — плохой UX.
**Предложение:** 
- Изменить схему настроек с одного `n8nBaseUrl` на **коллекцию environments** (массив объектов `[{name: 'Dev', url: '...', key: '...'}, ...]`) с возможностью выбора активного инстанса.

## 5. Token Limits & Chat Context Overflow
**Отмечено в спецификации:** Хранится `per-workflow chat memory`. Pipeline генерации динамически подтягивает полные параметры нужных нод из каталога.
**Где дыра:** Длинная история чата + большой текущий Workflow JSON + объемные схемы узлов могут быстро превысить окно контекста Claude (или стать неоправданно дорогими по токенам для каждой итерации). 
**Предложение:** 
- Регламентировать стратегию обрезки (Context Truncation) в `lib/chat-memory.js`: например, сохранять последние N сообщений + саммаризировать старые, или ограничивать передачу полного JSON текущего workflow, передавая только Diff/Blueprint, пока прямо не запрошена модификация.

## 6. Тестирование Shadow DOM (E2E)
**Отмечено в спецификации:** Playwright используется для E2E тестов.
**Где дыра:** Инжект в closed Shadow DOM означает, что Playwright обычными селекторами "не увидит" элементы интерфейса панели (кнопки, чат). 
**Предложение:** 
- В конфиг Playwright или тестовые сценарии нужно добавить явное использование Shadow DOM-piercing селекторов/движка. Либо для тестового окружения (process.env.TEST) запускать панель в mode: 'open'. 

---

**Резюме:** Сама архитектура PIVOT отличная, переход на Injected Side Panel решает фундаментальные проблемы юзабилити. Рекомендую в первую очередь закрыть вопрос с MV3 Service Worker Suspend, так как это прямо аффектит работоспособность базового флоу генерации.
